# Contributing to loopreel

Thanks for your interest in `loopreel`. This project is in early development, so the design is still moving. Please read this document before opening a pull request.

## Ground rules

- Be respectful and constructive in issues, reviews, and discussions.
- Open an issue before starting any large change (new adapters, changes to the trace format, changes to scheduling control). Small fixes and doc improvements can go straight to a PR.
- One logical change per pull request.

## No vibe coding

`loopreel` is a determinism tool. Its entire value is that replay behaves exactly like the recording, and subtle bugs in the recorder, the scheduler hooks, or the trace format silently break that guarantee. For that reason, **we do not accept vibe-coded contributions.**

**Vibe coding** means generating code with an AI tool (a chat assistant, an agent, or an autocomplete system) and submitting it without reading it line by line, understanding it, and verifying it yourself. Typical signs:

- You can't explain why the code is written the way it is.
- You couldn't have written it, or at least reviewed it with confidence, without the tool.
- The tests were generated by the same tool to match the code, and you haven't checked that they catch real failures.
- Large, sprawling diffs with unrelated changes, restructured files, or invented APIs and options.
- Answers to review questions that are pasted from a chatbot or that miss the point of the question.

### What this means for you

If you submit code, you are expected to:

1. **Understand every line you submit.** Maintainers may ask you to explain your design choices, and "the AI wrote it" is not an acceptable answer.
2. **Have written or personally reviewed and tested it.** You are the author and you are accountable for its correctness, whatever tools you used.
3. **Respond to review yourself.** Review discussions are between humans who understand the code.
4. **Disclose AI assistance.** If you used an AI tool in any meaningful way (beyond things like spell-checking or basic autocomplete), say so in the PR description and describe how you verified the result.

Using a tool to look up an API, explain an error message, or suggest an idea you then implement and verify yourself is fine. Submitting generated code you haven't mastered is not.

### What happens to vibe-coded PRs

Pull requests that appear to be unreviewed generated code may be closed without a detailed review. We may ask clarifying questions first. Repeated submissions of such PRs may lead to being blocked from the repository. We would rather receive a small, correct, well-understood patch than a large impressive-looking one.

This policy covers **code contributions**. Documentation fixes, bug reports, and design discussion are welcome regardless of how you wrote them, as long as they are accurate and you stand behind them. Please don't file AI-generated bug reports or security reports that you haven't verified.

## Development setup

Requires Python 3.11+ and [uv](https://docs.astral.sh/uv/).

```bash
git clone https://github.com/Omega-127/loopreel
cd loopreel
uv sync
uv run pytest
```

## Standards for code changes

- **Tests are required.** Every bug fix needs a regression test, and every feature needs tests. For anything touching recording or replay, include a test showing that replay reproduces the recorded behavior. Property-based tests with Hypothesis are encouraged.
- **Tests must be able to fail.** Before submitting, confirm your new test fails without your change.
- **No new core dependencies.** The core package is stdlib-only. Integrations belong in optional extras (for example `loopreel[httpx]`).
- **Trace format changes need discussion first.** The format is versioned, and changes require an issue and a version bump.
- **Be honest about determinism.** If your change introduces a case where replay might diverge, document it in the "What is and isn't guaranteed" section of the README.
- **Types and style.** Code must pass `ruff` and `mypy`:

  ```bash
  uv run ruff check .
  uv run ruff format --check .
  uv run mypy src
  ```

## Pull request checklist

Include this in your PR description:

- [ ] I linked the issue this PR addresses (for non-trivial changes)
- [ ] I read, understand, and can explain every line of this change
- [ ] I ran the tests, and the new tests fail without my change
- [ ] `ruff` and `mypy` pass
- [ ] I updated docs where behavior changed
- [ ] I disclosed any AI assistance below (or wrote "none")

**AI assistance disclosure:** _none / describe how you used it and how you verified the result_

## Commit messages

Write clear, imperative commit messages ("Add divergence check for time events"). Keep commits focused, and squash fixup commits before review.

## Reporting bugs

Please include:

- Python version and operating system
- `loopreel` version
- A minimal reproduction (ideally a small script and a trace file)
- Expected vs. actual behavior
- Which libraries are involved (`httpx`, `asyncpg`, etc.), and whether threads or C extensions are used

## Security issues

Traces can contain sensitive data. If you find a vulnerability (for example, a way traces leak secrets), please do not open a public issue. Contact the maintainer privately, using the email listed on the maintainer's GitHub profile.
